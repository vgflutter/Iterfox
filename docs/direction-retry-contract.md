# Bounded recovery of rejected direction proposals

This boundary is fixed before a separate reliability mission. It addresses the
observed self-dependency proposal that stopped the first real project session.
Do not change the active graph mission or its protected files.

After a provider successfully returns a structured orientation proposal, the
runtime can reject its semantic references: unapproved criteria, self/circular
dependencies, incomplete note accounting or an unsupported answer to a held
operator question. Let the same run ask the model to correct such a proposal with
concise validation feedback, without a new operator note or a fabricated Resume.
The failed attempt and its reason remain inspectable. A rejected proposal is
never an active direction, evidence, authorization or implementation.

Bound the consecutive invalid-proposal attempts using the original
`limits.maxAttempts`, including the first attempt. Each provider call consumes
the existing turn/token/time limits normally. Stop at whichever original limit
is reached first; never extend it, reset the clock, silently discard usage or
report completion while a current criterion or required review remains open.
Do not add configuration or scheduling machinery for this small recovery.

Only rejection of a returned proposal is eligible. Provider/authentication/network
or sandbox errors, protected-path changes, source audit failures and actual
reserved operator decisions retain their existing blocking behavior. Audit the
worktree before another model attempt, including when the proposal is invalid.
Do not weaken provider sandbox/authentication, check commands, thresholds, event
guards, held questions, protected paths or evidence freshness.

Keep incoming instructions through retries. Reconcile a complete ordered handoff
snapshot and leave newer instructions pending for the next boundary when needed.
The existing selected-node reference remains context, never extra authority.
Retire superseded planning activities through guarded, replayable state changes;
do not skip builders or acceptance checks. Pause/stop and explicit recovery must
continue to work. Preserve the first two milestones and all existing UI behavior.

The seven `tests/direction-retry.test.ts` cases use explicitly deterministic provider
faults and real runtime checks. They establish retry/state boundaries, not real
model reliability. The actual product mission separately uses real Codex and a
contextual instruction submitted from a real model-planned graph activity.
Document these distinctions and the observed outcome in
`docs/autonomous-recovery.md` and the READMEs. Do not claim that all failures or an
entire night can recover unattended.

The compatibility case uses an actual event stream generated by the frozen
pre-retry runtime, with a rejected orientation, explicit historical resume,
superseded-orientation event and successful real Node checks. The protected JSON
fixture fixes the canonical wire projection of every ledger prefix. New behavior
must not reinterpret those earlier events or historical states.

The existing Compass explicit-resume case uses a genuine provider interruption,
which remains blocking. Its superseded-planner and invalid-retirement assertions
are retained. A returned semantic self-dependency belongs to the new automatic
correction cases; requiring it to block immediately would contradict this approved
outcome. The frozen legacy ledger separately retains the older semantic
rejection/resume history without reinterpreting it.

After the reviewed delivery is collected, the existing real graph integration
can also be enabled with `ITERFOX_INJECT_DIRECTION_FAULT=1` alongside
`ITERFOX_REAL_GRAPH=1`. Its first successful real SDK orientation response then
receives one explicit synthetic invalid criterion reference. The same real SDK
must correct it without another operator note and complete the original checks.
The report identifies this injected fault and requires final structural contract
equality. This additional fixture does not claim a spontaneous model error.
